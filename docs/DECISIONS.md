# Product and Technical Decisions

This records the deliberate calls made on this project — what was decided,
why, and where it's enforced in code. It exists so a later contributor (or
a future version of the same developer) doesn't accidentally "fix" something
that was actually intentional.

## Accounts are admin-created, not self-service

**Decision:** Students and officials cannot create their own accounts.
Every account is created by an administrator (`POST /admin/users/students`,
`POST /admin/users/officials`), except the first admin account, which comes
from `app/scripts/seed_data.py`.

**Why:** This models how a real registrar's office actually operates —
enrollment and staffing are administrative acts, not self-service signups.
It also removes an entire class of problems (email verification, spam
accounts, identity fraud at signup) that a public registration form would
otherwise need to solve for an MVP.

**Where enforced:** There is no `POST /auth/register` or equivalent route at
all. An earlier direction that explored public self-registration (a
`pending_student_registrations` table) was abandoned before this decision
and its leftover table was dropped in migration `bbd08d7f2818` — it was
never wired to any route or frontend code.

## No role selector on login

**Decision:** The login form has one identifier field and one password
field — never a "log in as student / official / admin" choice.

**Why:** The role isn't the user's to declare. `POST /auth/login` resolves
the identifier against the database and returns the real
`account_type`/`role_key` from the matching row. A role selector would just
be a UI element the backend has to ignore anyway, since trusting it would
mean trusting the client to say who they are.

**Where enforced:** `app/api/routes/auth.py`'s `_find_user` — the backend
determines whether an identifier is a student ID, student email, or staff
email and looks up the account itself. `LoginRequest` has no role field.

## Backend is the source of truth, always

**Decision:** Role, office assignment, application ownership, registration
status, clearance status, completion percentage, and document access are
all decided by the backend on every request — never trusted from anything
the frontend sends or previously displayed.

**Why:** A frontend value is just a suggestion from an untrusted client. The
backend re-derives every one of these from the database on every call, so a
stale UI, a tampered request body, or a modified JWT payload can't change
what actually happens — see [ARCHITECTURE.md](./ARCHITECTURE.md#role-based-access).

**Where enforced:** Ownership checks in `application_service.py`,
`document_service.py`, `registration_service.py` (every lookup 404s for a
non-owner rather than trusting an ID alone); role checks in `app/api/deps.py`;
`overall_status`/`current_step` recalculated server-side after every
clearance change in `workflow_service.calculate_overall_status`.

## Hidden frontend links are not a security boundary

**Decision:** The frontend hides navigation a role can't use (an admin
never sees a "Student Portal" link, a student never sees clearance
decision buttons) purely for usability. This is never relied on for
security.

**Why:** Anyone can open dev tools or call the API directly. If hiding a
button were the only thing stopping unauthorized access, it wouldn't be
access control at all.

**Where enforced:** Every route in `app/api/routes/` independently checks
role/ownership via `app/api/deps.py`, regardless of what any frontend page
would have shown.

## Temporary passwords for MVP

**Decision:** Admin-created accounts get a temporary password — either
supplied by the admin or generated by the backend
(`core/security.generate_temporary_password`) — shown once in the creation
response, and never stored or returned in plain text again. The account's
`must_change_password` flag is set to `true`.

**Current status — enforcement is partial.** The flag is real: it's
persisted on `users.must_change_password`, returned by `/auth/login` and
`/auth/me`, and cleared by `POST /auth/change-password`. What is **not**
implemented is the frontend actually forcing a password-change screen
before letting a flagged account use the rest of the app — the session
carries the flag, but nothing currently acts on it. Do not describe this as
fully enforced; it is backend-supported, frontend-unenforced.

**Why deferred:** Building the forced-change UI (and deciding what "locked
out until you change it" should look like for each role) was judged
separable from getting the core account-creation flow working, and was
explicitly scoped out of the MVP pass that shipped it.

## One primary office per official

**Decision:** Each official account has exactly one office, chosen from a
fixed set of seven values, set at creation and changeable only through a
dedicated, confirmation-gated reassignment action.

**Canonical offices:** `REGISTRAR`, `HEALTH_SERVICES`, `SUCCESS_CENTER`,
`FINANCIAL_AID`, `BUSINESS_OFFICE`, `RESIDENCE_LIFE`, `PUBLIC_SAFETY`.

**Why:** The clearance workflow is built around exactly one office owning
exactly one clearance per application. Allowing multiple offices per
official would need the workflow, the queue, and the decision endpoint to
all resolve "which clearance does this action apply to" ambiguously instead
of directly from the session.

**Where enforced:** `app/core/enums.py`'s `OfficeKey` enum is the only
accepted value anywhere an office is set (creation, reassignment) — there
is no free-text office field. `PUT /admin/officials/{id}/office` is the
only route that changes it after creation, and the Office Assignments
screen requires confirming before submitting.

## No admin-created admins in the MVP

**Decision:** `POST /admin/users/officials` accepts only the seven office
values above — `system_admin` is not one of them, and there is no
`POST /admin/users/admins` route at all. The first (and, in this MVP, only
practical way to create another) admin account comes from
`app/scripts/seed_data.py`.

**Why:** Limits the blast radius of a compromised or careless admin
account, and keeps "who can grant admin access" outside the running
application entirely for now — a deliberate, conservative default rather
than an oversight.

## Public Safety is an in-person stage, not a form

**Decision:** Public Safety has no online wizard step. Its clearance is
created with `status = IN_PERSON_REQUIRED` the moment an application is
submitted, and only a Public Safety official completing an in-person
verification moves it to `approved`.

**Why:** Student ID processing genuinely requires a physical visit — a
photo ID has to be checked and a card issued in person. Pretending this
could be an online form would mean the "completed" status could be reached
without anyone ever verifying identity in person, which defeats the point
of the step.

**Where enforced:** `workflow_service.get_initial_clearance_state`'s
`public_safety` branch; `workflow_service.build_public_safety_instruction`
generates the instruction object every registration submission and status
check returns until that clearance is actually approved.

## Residence Life is conditional on residency

**Decision:** A residential student's Public Safety clearance depends on
Residence Life approving first. A commuter student's Residence Life
clearance is created already `not_required`/`completed`, and Public
Safety's prerequisite becomes Business Office approval instead.

**Why:** Housing confirmation only makes sense for students who are
actually being housed. Forcing a commuter through a Residence Life gate
they have no reason to clear would block registration for no reason.

**Where enforced:** The `clearance_dependencies` table (seeded in
`seed_data.py`), evaluated by `workflow_service.unlock_ready_clearances` —
this is data, not a scattered if/else, so the rule is visible and testable
in one place.

## Transcript upload is optional for MVP

**Decision:** A transcript can be uploaded at the Success Center step, but
nothing in the backend or frontend requires one before submitting or
completing registration.

**Why:** No institutional confirmation exists (in this repository) that a
transcript is mandatory for every student at this stage — treating it as
optional avoids inventing a requirement that hasn't been confirmed.
**Requires institutional confirmation** if this should change.

## Accounts are deactivated, never deleted

**Decision:** `POST /admin/users/{id}/deactivate` sets `is_active = false`.
There is no delete-user route.

**Why:** Preserves the audit trail and every application/clearance record
tied to that user. A deactivated account can't log in
(`app/api/deps.py`'s `get_current_user` rejects inactive users), but every
record they own or acted on stays intact and queryable.

## Document uploads live inside the registration step that owns them

**Decision:** There is no separate "Upload Documents" step in the
registration wizard. Each step uploads directly to
`/registrations/{id}/documents` (or the legacy
`/applications/{id}/documents`) as soon as a file is selected.

**Why:** A document only makes sense in the context of the office that
needs it (a photo ID belongs to Welcome Desk, an immunization record to
Health Services). Separating "fill out the form" from "attach the file"
into two different places would make it easy to submit a step with a
missing required document without noticing until the very end.

## Unresolved / open questions

Recorded honestly rather than silently decided one way:

- **Forced password change** — the flag exists; the enforcement UI does
  not. See "Temporary passwords" above.
- **Resubmission after a correction request** — there's no distinct
  "resubmit" action; a student addresses a correction by re-uploading a
  document or contacting the office, and the same office reviews it again
  through their normal queue. Whether a dedicated resubmit flow is needed
  is open.
- **Document storage** — local disk only. Moving to object storage (e.g.
  S3) and adding real malware scanning (the `virus_scan_status` column
  exists but nothing sets it past `pending`) are both future work, not
  started.
- **Deadlines / active registration term** — the backend has no concept of
  a registration window or deadline; a draft can be started and submitted
  at any time. Whether/how to add an active-term concept is open and would
  need institutional input.
- **Email notifications** — every notification is in-app only. Whether
  students/officials should also get email is unresolved.
